# karLook

A static, SEO-conscious foundation for a Melbourne chauffeur and private transfer brand. This is a non-transactional prototype: enquiries are not yet open, bookings require manual confirmation, and no payments are collected. Fleet examples are illustrative; business contact details and credentials have not been invented.

## Stack

- Astro 7 with static output and React islands for interactive navigation
- TypeScript with Astro's strict configuration
- Tailwind CSS 4, custom design tokens and Lucide icons
- ESLint, Prettier and GitHub Actions

## Getting started

Use Node.js 24 and npm. Install and start the development server:

```sh
npm ci
npm run dev
```

Other commands:

```sh
npm run check          # Astro and TypeScript diagnostics
npm run lint           # ESLint
npm run test:booking   # Booking validation and adapter tests
npm run test:pricing   # Route and pricing tests
npm run images:optimise # Regenerate responsive WebP variants
npm run audit:seo      # Audit the generated dist/ output
npm run build          # Static output in dist/
npm run preview        # Preview the production build
npm run format         # Format files
npm run format:check   # Check formatting
```

## Structure

```text
src/components/common/       Shared buttons, containers and states
src/components/navigation/   Header, footer and React mobile menu
src/data/                    Typed business configuration and static page content
src/layouts/                 Shared layout and metadata
src/lib/seo/                 SEO helpers
src/lib/paths.ts             Base-aware links and assets
src/pages/                   Astro routes and static 404
src/styles/                  Design tokens and responsive styles
public/                      Static images, favicon and llms.txt
.github/workflows/           GitHub Pages build and deployment
```

The general content routes are generated by `src/pages/[...slug].astro` from `src/data/pages.ts`; fleet routes use `src/data/vehicles.ts` and are pre-rendered separately. Edit that typed file to replace the demonstration models, images, capacities, features and publication flags with verified information. Fleet filters and comparison run locally in the browser. The shared configuration in `src/data/site.ts` contains empty placeholders for phone, email, WhatsApp, address and social accounts. Fill only with verified details; WhatsApp should include the country code. Contact details appear on the contact page when configured. Booking remains intentionally disabled until an enquiry channel is implemented.

Service pages use `src/data/services.ts` and `src/data/service-faqs.ts`. Services are currently proposed, and their `verified` flags are false. Destination content and relationships live in `src/data/destinations.ts`; every destination has `active` and `published` set to false, so no individual destination route is generated. Verify the business's service coverage and each page's local content, then set both flags before publishing a destination. Review service copy and operations before setting a service's `verified` flag. The destination overview and planner clearly identify proposed areas.

## Site URL and base path

Set `PUBLIC_SITE_URL` only after a real custom domain is verified, to its HTTPS **origin** without a path. GitHub Pages preview origins, localhost and IP addresses are rejected. Set `ASTRO_BASE` to `/` for the custom domain or user/organisation site, or `/repository-name/` for a project site. Without the production origin, pages are `noindex, nofollow`, canonical URLs are omitted, and no sitemap is generated. The GitHub Pages workflow supplies its deployment origin only for absolute Open Graph and Twitter image URLs; this does not change canonical or indexing behavior. Unconfigured local builds omit social image URLs unless `PUBLIC_SHARE_ORIGIN` is supplied. Both origin variables are build-time values, not secrets. For a local test build only, export an example origin in the shell:

```sh
PUBLIC_SITE_URL=https://example.com ASTRO_BASE=/repository-name/ npm run build
```

`.env.example` documents the variables; export them before running Astro if using an `.env` file. Do not put secret keys in client code or static build variables.

## GitHub Pages

1. Initialise a Git repository, push it to GitHub, and select **Settings > Pages > Build and deployment > Source: GitHub Actions**.
2. Push to `main` or run the deployment workflow manually. The workflow obtains the repository base path from `actions/configure-pages`; it does not use the GitHub Pages origin as a canonical URL.
3. Keep `PUBLIC_SITE_URL` unset while using a GitHub Pages preview. Once a custom domain is verified, set repository Actions variables `PUBLIC_SITE_URL` to its HTTPS origin and `ASTRO_BASE` to `/`.
4. Verify the deployed home page, navigation, images and direct links. Each route is a static `index.html` and supports direct navigation and refresh. GitHub Pages serves `404.html` for missing paths; project-site 404 behaviour is controlled by GitHub Pages.

The workflow deploys a Pages artifact and includes `.nojekyll`. It does not create a repository or set up a domain.

## Custom domain

After acquiring a domain, configure it in GitHub Pages settings and follow GitHub's DNS and domain verification guidance. Set the Pages Actions variables to the verified HTTPS origin and `/`, then redeploy. When deploying via GitHub Actions, configure the domain in Pages settings; a `CNAME` file is not required in the artifact. Enable HTTPS after DNS verification. Do not commit an assumed domain.

## SEO and content

Each page has a title, description, robots directive, canonical URL when configured, Open Graph and Twitter metadata, semantic landmarks and Australian English language declaration. The sitemap is generated from Astro's published routes and excludes noindex booking, legal, 404 and illustrative vehicle pages. The generated `robots.txt` links to the sitemap when a production origin is configured and does not block assets. On a GitHub project site, `/repository-name/robots.txt` is not the host-root robots file; the preview's page-level noindex directives remain essential.

Organization, WebSite and BreadcrumbList JSON-LD are emitted only with a configured production origin. LocalBusiness requires `verifiedLocalBusiness` plus a complete verified Victorian address in `src/data/site.ts`; the same address is shown on the site. Service JSON-LD is emitted only when its service is verified. No FAQPage or Product rich-result markup is fabricated. See `docs/seo-audit.md` for the audit, keyword mapping, performance measurements and search-engine verification checklist.

## Booking application

The homepage planner transfers its journey directly into an in-memory booking overlay; fleet, service and destination links use non-sensitive IDs to preselect preferences. The booking application validates Melbourne-local pickup and return times, including daylight-saving transitions, and validates Australian mobile numbers. It never writes names, contact information, addresses, flight numbers, instructions or other personal details to browser storage or URLs. Only non-sensitive journey preferences and an idempotency identifier are retained in session storage; they are cleared on completion or cancellation. Personal details and acknowledgement details disappear on reload, so a direct visit to the confirmation route cannot manufacture a receipt.

All current fleet records are illustrative and are excluded from booking selection. Add verified vehicles to `src/data/vehicles.ts` and set `demonstration` to false before they appear; set `capacityVerified` only when both passenger and luggage capacities have been verified. Unverified capacities are never used to exclude a vehicle. Actual vehicle allocation remains subject to manual confirmation.

With no API configured, the production build cannot submit. The development server offers a **clearly labelled simulation** that sends nothing; set `PUBLIC_BOOKING_MOCK_FAIL=true` only while developing to exercise failure handling. A simulated reference is not an enquiry receipt. The privacy and terms pages are placeholders and must be replaced with approved policies before live enquiries open.

To enable a real endpoint, configure `PUBLIC_BOOKING_API_URL` as a public HTTPS URL at build time (or as a GitHub Actions repository variable). It is visible to every browser and must never contain a secret or credential. Local HTTP endpoints are allowed only by the development server. The client sends a JSON `POST` with `clientRequestId`, `createdAt` and `booking`, and the same UUID in an `Idempotency-Key` header. Requests omit browser credentials and referrers and reject redirects. Only a successful HTTP response with JSON `{ "status": "received", "reference": "..." }` displays a received acknowledgement. A reservation is never confirmed by the frontend. The backend must enforce durable idempotency for that key, reject changed payloads for a reused key, validate every field and allowed service/vehicle, and return a reference made of letters, digits, hyphens or underscores. Configure CORS for the actual site origin and the `Content-Type` and `Idempotency-Key` headers.

## Future production and booking

Move the generated static output to a commercial static host or adopt an Astro server adapter as requirements evolve; keep the public origin and base configured for the new host. Address search and route estimation have backend adapter interfaces, but no real provider or rates are configured. The optional `PUBLIC_ROUTE_DEMO` uses clearly labelled simulated routes and must not be used for live enquiries. Implement the booking API with server-side validation, HTTPS, durable idempotency, spam protection, rate limits, secure logging, access controls, retention and deletion policies, and explicit consent. Keep Supabase, maps, email and WhatsApp credentials server-side. Configure verified support channels and send notifications only through confirmed provider responses. No live distance, price, payment, availability or transactional booking is provided by default.
